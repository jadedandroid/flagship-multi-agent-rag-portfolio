PROJECT 02 · SIMULATION

Incident response that waits for human approval.

An event-driven cloud-cost and incident-remediation design: anomaly intake, bounded diagnosis, proposed intervention, explicit approval, simulated execution, and an append-only audit record.

This page describes a simulation design only. It has no cloud credentials and cannot alter infrastructure.

CONTROL FLOW

Propose, review, verify

  1. SignalParse a synthetic CloudWatch/Prometheus event and validate its schema, timestamp, and resource identifiers.
  2. DiagnoseCorrelate the signal with a bounded set of known runbooks; preserve evidence and uncertainty.
  3. PlanDraft a reversible action, estimated blast radius, expected cost impact, rollback, and verification checks.
  4. ApproveRequire an authenticated human to review and approve the exact plan digest. No approval means no action.
  5. Simulate and verifyApply the change to a local scenario model and append the result and verification outcome to the audit ledger.

SAFETY BOUNDARY

No live operations

The portfolio version does not connect to AWS, execute Lambda or Step Functions, inspect real accounts, or prune resources. A future adapter must use least-privilege credentials, idempotency, scoped approvals, independent post-action verification, and an emergency stop.

AUDIT MODEL

Decision provenance

A production ledger would record immutable event IDs, timestamps, normalized input hashes, evidence references, proposed-action digest, approval identity and token ID, execution result, and verification checks. Do not store raw cloud credentials or approval secrets in the ledger.
